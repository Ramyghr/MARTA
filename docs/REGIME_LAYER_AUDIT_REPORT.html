1. Executive Summary

1.1 Headline verdict

Is the regime representation layer valid to build on?

Technically, yes now — the engine is correct, the panel is clean, and the discovered states are statistically genuine volatility regimes, reproducibly so. Practically, no — a minimal, honest backtest (Phase 6) found that conditioning position sizing on the regime label does not measurably beat simply using continuous realized volatility directly, in either a strong bull year (2024) or a decline (2025). Both approaches underperformed plain buy-and-hold in both periods.

This session started as a file-by-file audit of the data pipeline and Gaussian HMM regime-clustering layer, prompted by a growing pile of unresolved questions about whether the regimes the project has been conditioning agents and an RL policy on were ever actually valid. It ended as a full rebuild-in-place: three real engine bugs fixed, one methodological pivot (the original 4-asset panel was quietly detecting asset identity, not market regime), five newly engineered validation tools generalized for reuse against any future candidate model, and a final downstream test that answers the question this whole project keeps returning to — does any of this help.

2.2 File-by-file audit findings (condensed)

A full file-by-file pass covered every file in pipeline/ and regime/ plus configs/splits.py, configs/assets.yaml, and utils/assets.py. Full detail lives in the session transcript; the load-bearing findings are summarized below by layer.

Data pipeline (pipeline/*.py)

  • fetch.py: CCXT loop-termination bug (previously capped ETH at 2021) was already fixed; OHLCV sanitization causal and correct; gap detection is log-only, never blocks the pipeline.
  • normalize.py: the 720h rolling z-score is causal (no train/val/test leakage — each row's z-score only depends on its own trailing 30 days) but this also means no feature can carry a signal that persists longer than 30 days — a direct candidate explanation for why measured HMM dwell times (13–20h) are far shorter than a classical multi-week "market regime."
  • validate.py: solid structural/range/gap/distribution checks; no formal stationarity test existed anywhere in the codebase before this session.

Representation & HMM engine (regime/hmm.py)

  • PCA fit train-only (correct, no leakage).
  • Two real bugs already fixed before this session began: a covariance-type mismatch (full vs. diag) that let one state's covariance run away unconstrained, and a BIC flat-curve guard that only ever compared the top-2 candidates (meaningless at this data scale — degenerated to always dropping exactly one state from the search grid).
  • Two bugs still present at session start (fixed in Phase 1, §3): fit_hmm_bic subsampled 20,000 random, non-contiguous rows and fit them as one sequence for the BIC search — corrupting the estimated self-transition probability; and no call anywhere passed lengths=, so every multi-asset embedding matrix (4+ assets' full histories concatenated) was fit and Viterbi-decoded as if the last row of one asset transitioned directly into the first row of the next.

3. Phase 1 — Engine Correctness & Robustness

Goal: fix the HMM fitting engine itself, independent of any data/panel decision, and prove the fix doesn't change anything that was already correct before touching real data.

3.1 What changed in regime/hmm.py

  • _compute_lengths() — contiguous per-asset run lengths, computed from the asset-label array, passed as lengths= to every .fit() / .score() / .predict() / .predict_proba() call. Multi-asset sequences are now modeled as independent chains, not one continuous sequence.
  • fit_hmm_bic rewritten — no more subsampling; every BIC candidate is fit on the full, correctly-segmented training data. Slower, not wrong.
  • _fit_multiseed() — the final refit is now best-of-5 independent EM runs from different random initializations (hmmlearn has no built-in n_init/restart mechanism, so this is a manual equivalent), keeping the highest-training-log-likelihood model. Returns a seed-sensitivity report: per-seed log-likelihood/convergence, and pairwise Adjusted Rand Index / Normalized Mutual Information between every pair of seeds' decoded labels.
  • Saved alongside every checkpoint as seed_sensitivity.json and logged to MLflow.

3.2 Gate check — does the fixed engine reproduce production's known-good result?

Ran the fixed engine against a copy of production's actual embeddings, forcing n_states=4 to match. Resulting regime distribution — 23.5% / 23.8% / 28.7% / 23.9% — matched regime_semantics.json's historical values almost exactly. The contamination guard test (scripts/audit_phase0_invariants.py) still passed. Gate passed — the fixes changed nothing that was already correct.

New finding, not part of the original plan The seed-sensitivity check this phase added surfaced something the original audit missed entirely: at production's n=4, five independent EM seeds produced mean pairwise ARI = 0.193, min ARI = 0.010 — two of five seed-pairs landed within noise of chance agreement. Log-likelihoods across seeds varied by only 0.6%, meaning there are multiple similarly-good but structurally different local optima. Production's checkpoint happens to use seed 42, which won this particular best-of-5 comparison by log-likelihood — so nothing about the deployed artifact needed to change immediately — but this proves the seed choice was luck, not evidence of a well-identified clustering.

Cheap side-check: is n=4 simply "too many states," or is instability structural?

3.3 An engineering detour: the deadlock

Bug found mid-session Parallelizing the 5-seed refit with Python's default fork()-based ProcessPoolExecutor deadlocked completely on real data — 17 minutes elapsed with 5 worker processes sitting at 0.1% CPU each (~1 second of actual compute accumulated). Root cause: the BIC-search fit immediately before the pool launch does enough NumPy work on a quarter-million-row matrix to trigger OpenBLAS's multi-threaded worker pool in the parent process. Forking while those threads are active duplicates only the calling thread — any mutex another BLAS thread was holding at fork time stays "phantom-held" forever in every child, so the first BLAS call in each worker hangs indefinitely.
Fix Switched ProcessPoolExecutor to the spawn context — each worker starts as a genuinely fresh interpreter, no inherited thread/lock state. Verified directly: after the fix, all 5 spawned workers sat at 97–98% CPU (not 0.1%), completed a 250K-row synthetic sanity check in 488.9s with zero errors, and gave the theoretically-correct result (mean ARI ≈ 0.003 on pure random noise, i.e. chance-level agreement, exactly as expected when there's no real structure to find).

4. Phase 2 — Normalization Horizon Experiment

Goal: test whether the production 720h(30-day) rolling z-score is silently capping how long a "regime" the HMM discovers can persist, and add the stationarity testing that never existed.

4.1 What was built

normalize_features_multihorizon()
Added to pipeline/normalize.py, purely additive — production's 14-column normalize_features() path is completely untouched. Adds a 90-day (2160h) and 180-day (4320h) rolling z-score, in addition to the production 720h one, on four vol-shape features: realized_vol, atr, bb_width, vol_ratio. Deliberately reuses the same min_periods=168 as the production window rather than scaling it up, so the longer horizons don't drop any extra warmup rows — output is 22 columns (14 + 8).
regime/stationarity_check.py
New. Runs ADF (H0: unit root) and KPSS (H0: stationary) on every feature column, per asset. "Confirmatory stationary" = both tests agree. Generalized via CLI args (--assets, --tag) for reuse against any panel.

4.2 Two bugs found and fixed while building this

Bug First run crashed outright: ValueError: Invalid input, x is constant on EURUSD's vol_zscore/obv_raw column — independent, accidental confirmation that histdata's zero-volume FX/commodity features really are literally constant, not just near-constant, exactly the mechanism later shown to cause the asset-collapse problem (§5).
Bug adfuller's autolag="AIC" exhaustively re-fits an OLS regression per candidate lag order — at ~45–75K rows × 14 columns × several assets, this took ~14 minutes per asset.
Fixes Degenerate/near-constant columns (std < 1e-10) are now detected and reported explicitly instead of crashing. Lag order switched to a fixed value via Schwert's (1989) rule of thumb, computed once per series instead of searched — cut runtime to well under a minute per asset with no material loss of validity at this sample size.

4.3 Result — a different, more valuable finding than the one hypothesized

The direct hypothesis (longer horizon → longer regime dwell time) was not confirmed: measured dwell time on the multihorizon feature set was flat to slightly shorter than the 720h-only baseline. But the seed-sensitivity check (added in Phase 1) revealed something arguably more important — see §7 for the full numbers once tested on the real panel in Phase 5: the 22-column multihorizon set drives seed-stability from ~0.585 to ~1.000 on the crypto panel, at the cost of somewhat weaker return distinctness. A real trade-off, not a clean win either direction — detailed in §7.3.

7.4 The two robust findings from this matrix

Finding 1 — as robust as this kind of analysis gets realized_vol_raw distinctness is p≈0 in every one of 6 independently-fit models, every asset tested, no exceptions. These are genuine, statistically real volatility regimes, full stop, regardless of panel or feature-horizon choice.
Finding 2 — equally robust, opposite direction regime_only next-bar directional AUC is chance-level (0.49–0.52) in every one of the same 6 models. The regime label carries no measured directional predictive signal, independent of asset count, panel choice, or feature horizon.
A genuine trade-off, only visible once every variant was tested 14-column features give better close_return distinctness than the 22-column multihorizon set (crypto5: 4/5 assets significant vs. 2/5), but the 22-column set gives dramatically better seed-stability (0.99–1.00 vs. 0.59–0.70). Neither is a clean win. Given regime_only AUC is chance-level either way, the extra return-distinctness the 14-column set buys was never translating into usable directional signal — which is why the multihorizon set is still the better default for anything meant to be reproducibly deployed, but this is a judgment call on a real trade-off, not an obviously-correct choice.

8. Phase 6 — Regime-Conditioned Backtest

Goal: the question every prior phase was in service of. Does conditioning on the regime label improve risk-adjusted returns? Minimal, self-contained (regime/phase6_regime_backtest.py) — no RL/PPO, no LLM/agent layer, no encoder. Just price data and the regime label already sitting in regime_stream.parquet.

8.1 Design

Given regime already showed no directional signal (§7.4), the honest question isn't "can regime predict direction" — it's "does discretizing volatility into regime buckets, for position sizing, beat just using continuous volatility directly." Three long-only strategies, sharing the same directional signal (always long, isolating the sizing question from any directional edge that's already known not to exist):

buy_hold
weight = 1.0, constant.
vol_target_continuous
weightt = clip(target_vol / realized_vol_rawt-1, 0.1, 2.0) — regime-free, uses the asset's own trailing realized vol directly.
regime_conditioned
weightt = clip(target_vol / regime_vol_map[regime_labelt-1], 0.1, 2.0) — regime_vol_map is the mean realized_vol_raw per regime, computed on train data only (<2024), leakage-safe.

target_vol = train-period mean realized_vol_raw, so both sized strategies run at the same average exposure as buy-hold over the period the mapping was learned on — a fair comparison, not just "trade smaller." Weight decisions use only t-1 information, applied to the t-1→t return — no lookahead. Transaction cost: 5bps per unit of weight change. Evaluated on the project's existing walk-forward val(2024)/test(2025) split. Confidence intervals via block bootstrap — 1000 resamples, 168-hour (1-week) non-overlapping blocks, seed 42 — the identical methodology rl/ablation.py's bootstrap_sharpe_ci already uses elsewhere in this project, reimplemented standalone here so this script has zero dependency on the RL layer.

8.3 Interpretation

  1. Vol-based sizing hurt in both tested periods. 2024 was a strong bull run (buy-hold Sharpe 1.2–1.5); cutting exposure during high-vol windows meant missing exactly the moves driving those returns — the well-known failure mode of vol-targeting in strong trending markets. 2025 was a broad decline where it didn't help either. Notably, both sized strategies actually ran at higher average exposure than buy-hold (1.2–1.6× vs. 1.0×, since 2024/2025 realized vol came in below the training-period target) — this isn't a story about being too conservative, they were more aggressive on average and still underperformed.
  2. Regime-conditioning adds nothing measurable over continuous realized volatility for this sizing use case. All four bootstrap CIs straddle zero. The entire HMM apparatus — fitting, seed-selection, distinctness testing — produces volatility buckets that are statistically real (§7.4, finding 1) but functionally interchangeable with a much simpler "divide by trailing realized vol" rule, at least for this strategy shape.
  3. Real per-asset heterogeneity exists — BNB is the one asset where continuous vol-targeting actually beat buy-hold; LTC and XRP degraded the most under either sizing scheme. Not a uniform story across the panel.

Bottom line

On this minimal, honest test, conditioning on the regime label does not improve risk-adjusted returns, and does not distinguishably beat simply using continuous volatility instead. This is a real, negative-leaning result — not a data-quality artifact. The representation layer itself is now in genuinely good technical shape (no asset-collapse, near-perfect seed stability, statistically real volatility distinctness) and it still didn't clear this bar. It tested exactly one strategy shape (long-only, vol-target sizing) over two periods — it does not rule out regime having value in a different use (directional conditioning combined with other signals, cross-asset correlation-aware allocation, or as one input among many in a learned policy that can find a nonlinear combination) — but the simple, standalone case for this regime layer is not there.

10.2 What's now true about this layer

  • The HMM fitting engine is methodologically correct: sequence boundaries respected, no subsampling artifacts, multi-seed robustness measured and reported by default on every future fit.
  • The crypto-only panel (BTC/ETH/BNB/LTC/XRP) is clean: no asset-collapse, formally validated by pipeline/validate.py, empirically-checked n_states with no duplicate/flicker states across a wide swept range.
  • The discovered regimes are genuine, statistically real volatility states — the single most robust finding in this entire audit, replicated across 6 independent model fits with zero exceptions.
  • Every validation tool built this session (stationarity, distinctness/predictive audit, n_states sweep, panel builder) is now generalized via CLI args and reusable against any future candidate model with no code duplication.

10.3 What's still true, and matters more

  • The regime label carries no directional predictive signal, in any configuration tested.
  • Regime-conditioned volatility-based position sizing does not measurably beat simply using continuous realized volatility directly — the entire value proposition of building an HMM over just computing a trailing volatility statistic did not survive contact with an honest backtest.

10.4 Recommendation for the next layer

Given Phase 6's finding, the LLM/agent deliberation layer and the RL execution layer should not assume regime conditioning is a source of value by default. Two honest paths forward: (a) treat the regime vector as one weak input among many in a learned policy (RL/PPO) that can discover a nonlinear combination no simple rule-based test like Phase 6 could find — the original design intent — accepting that its marginal contribution may be small; or (b) deprioritize the regime layer's role in the next phase and focus compute/attention on components with a more directly demonstrated edge. This report does not recommend one over the other — that is a project-priority decision, not an engineering one — but it removes the option of proceeding on the unexamined assumption that regime conditioning obviously helps. It doesn't, at least not in the way tested here.
